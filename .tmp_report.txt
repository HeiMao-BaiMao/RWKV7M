この文書の位置付け
====================

本書は、0.185B Screening v5 の synthetic retrieval 学習で観測された
memory非利用・学習不安定性を切り分けるための作業記録である。アドバイザーへ
共有できるように、確認済み事実、推論、反証された仮説、無効な実験、未検証事項を
分けて記載する。

重要な注意:

- MiniPile magic sampler + carry_state=false はmemory品質ゲートとして不適切である。
  今回の品質評価にはdocument単位のsynthetic delayed key-value retrievalを使った。
- ROCm実行はbitwise deterministicではない。同じcheckpointとデータ位置からの再開でも
  loss軌跡とNaN発生stepが一致しない。このため単一runの成否を原因証明に使わない。
- 一部のresume ablationはCLIバグによりoverrideが適用されておらず、無効である。
  該当結果は下記で明示する。

3. write threshold warm-upの設計バグ
==================================

確認済み事実:

低load時のpermissive threshold warm-upがreadだけでなくwrite/noveltyにも適用されていた。
occupied slotが1個のときwrite tauが約-0.2まで下がり、最初のslotがほぼ全tokenへ
matchするため、1-slot collapseを自己強化していた。

修正:

commit cc3e42c "Separate screening read and write warmups"

- capacity tau helperへwarmup_by_loadを追加
- low-load warm-upはread thresholdだけに適用
- write/novelty thresholdは常にcapacity-calibrated値を使う
- 回帰testを追加

修正前0.185B run（/root/RWKV7M/out/retrieval-185m-run-s1001）:

- step 104: slot利用はほぼ1 slot
- step 236: 一時的にslot utilization約0.275、hard write約0.289
- step 400: slot utilization=0.0625、hard write=1/512、soft write約0.494
- 結果: 1-slot解へ再collapse

修正後はslotが複数使われるようになり、この特定のcollapse原因は解消した。

8. Pallas WKV backwardの逆算バグ
================================

初期観測:

- checkpoint 205からPallas/Triton WKVはstep 211でNaN
- 同checkpointからreference lax.scan WKVはstep 215までfinite
- Pallas約8.7k tok/s、reference約3.18k tok/s

コード監査で、Pallas backwardが次式でprevious stateを逆算していた。

  previous_state =
      (current_state - rank_updates) / decay

  decay = exp(-exp(w))

adversarial最小再現:

- T=32, B=1, H=1, N=64
- 1 tokenのwだけ5.0に設定し、FP32 decayを0へroundさせた
- reference: loss/全gradient finite
- Pallas: r, w, neg_kk gradientがnonfinite

これは実機で再現できるアルゴリズム上の欠陥である。ただし実モデルのwは
softplus clampで負側へ制約されるため、このadversarial条件だけが実学習NaNの
主因とは限らない。

修正:

commit 2599ad5 "Stabilize Pallas WKV backward state reconstruction"

- primal forwardでは不安定なinverse-reconstruction tapeを保持しない
- VJP内でforwardを再実行し、tokenごとのFP32 state tapeを作る
- backwardはcheckpoint[t]からprevious stateを直接読む
- GPU/TPU両Pallas backendへ同じcorrectness contractを適用
- checkpoint_interval != 1のbackwardはfail-fast
- decayが0へroundする回帰testをGPU/TPU両backendへ追加

修正後MI300X:

- adversarial real-accelerator test: GPU/TPU指定backendともpass
- checkpoint 205からstep 225まで20 step全てfinite
- steady Pallas throughput約8.16k tok/s
- reference約3.18k tok/sに対し約2.6倍
- 旧Pallas約8.7k tok/sから約6%低下

ただし、その後の長期runはstep 244でNaNとなり、reference WKV対照もstep 248で
NaNとなった。従ってinverse reconstruction bugは修正必須だが、長期NaNの唯一原因
ではない。Pallas固有原因という仮説は反証された。


9. parameter storage dtypeとcompute dtypeの分離
================================================

FP32 parameter storageを対照実験しようとしたところ、学習開始前に次の契約違反を
検出した。

- r: BF16
- w: FP32
- WKV input dtype validationで停止

原因:

- NNX Linearの多くはcompute dtypeを指定していた
- しかしTimeMix/ChannelMixのraw parameterを直接使う加算・乗算がFP32 parameterに
  よってactivationを暗黙にFP32へpromoteした
- tiled LM headもFP32 storage kernelをそのままmatmulへ渡していた

修正:

commit 8e9b5a6 "Separate NNX parameter storage from compute dtype"

- TimeMix raw parametersを演算前にcompute dtypeへcast
- ChannelMix time-mix parameterも同様にcast
- tiled LM head kernelをnormalized hidden dtypeへcast
- BF16 compute + BF16/FP32 parameter storageの両方を回帰test化

実機ではFP32 parameter storage + BF16 computeが約7.9--8.0k tok/sで動いたが、
step 156でNaNとなった。FP32 storageはdtype契約として有効になったが、今回のNaNを
解決しなかった。従ってpresetの既定値変更はまだ行っていない。

12. 現時点の判断
=================

確認済み:

1. magic sampler + carry_state=falseはmemory品質評価に不適切。
2. synthetic document retrieval + streaming evalは必要な評価vehicleを提供する。
3. write thresholdへread warm-upを流用したことが1-slot collapseを強めていた。
4. memoryはstep 205時点でlogitへ非ゼロ効果を持つが、retrieval精度はchance。
5. trunk-onlyはLR=1e-4で少なくとも300--500 step相当finite。
6. Screeningがlossへ接続されたrunでのみ長期NaNを観測した。
7. Pallas WKV inverse reconstructionには独立したcorrectness bugがあった。
8. そのPallas bugを直してもreference WKVでNaNが出るため、長期NaNの主因は別。
9. FP32 parameter storage対応は必要なdtype修正だが、NaN解決にはならなかった。
10. ROCm trajectoryは非決定的で、NaN発生stepは再開ごとに変わる。

最も妥当な現在仮説:

- Screening recurrence/auxiliary objectiveから流れるgradientのどこかが、hard routing
  境界とROCmの微小な数値差によって稀に非有限updateへ入る。
- 特にactivation ramp中に失敗が集中するが、memory residualと各aux lossの寄与は
  有効なablation完了前なので未確定。

反証された、または証拠不足の仮説:

- 「Pallas WKVだけが原因」: reference WKVでも失敗したため反証。
- 「BF16 parameter storageだけが原因」: FP32 storageでも失敗したため反証。
- 「checkpoint 200のoptimizer stateが既に壊れている」: fixed-step gradient/updateが
  全finiteで、複数resumeがstep 205を通過したため反証。
- 「self-index単独が原因」: 一見そう見える時系列はあるが、有効な単独ablationが
  未完了なので未確定。

17. 外部評価を受けた§15の解釈修正
====================================

Fable 5による§15の評価を、以下のように採用する。

確認された事実:

- no-auxではhard writeが約0.997--0.999へ飽和し、noveltyもほぼ1.0である。
- 同時にscreening/base RMS ratioは3e-5--5e-5程度で、memory branchの
  trunk出力への寄与は非常に小さい。
- 旧runでの全拒否と今回の全受理は鏡像の端点解であり、現在までに安定した
  中間write率を長期維持した例はない。

表現を弱めるべき点:

- §15のstep 220 finiteだけから「aux無しなら安定」とは結論しない。
- 既知のPallas/reference失敗例はstep 244/248にもあり、ROCm trajectoryも
  非決定的である。§15が直接支持するのは「この1 runではstep 220までfinite」
  および「activation ramp中の既往多発帯を一度通過した」までである。
- no-aux runは最低step 300--400へ延長し、可能なら複数seed/resumeで失敗率を
  見る必要がある。

設計上の最も妥当な推論:

- memory residualが極小の間、CEはrouting policyへ十分な監督信号を提供して
  いない可能性が高い。現行のaux lossはroutingに対して実質的な主目的関数に
  なっている。
- softなfloor/budget lossだけでは、hard forwardの実現write率とのGoodhart gapを
  閉じられない。
- write率そのものを損失勾配だけで制御する方式には、端点飽和、弱すぎる制約、
  急峻な制約による不安定化という共通リスクがある。

次の実験優先順位:

1. self-index-onlyをcheckpoint 100から有効にしてstep 300以上まで実行。
2. self-index-onlyが失敗する場合、self-indexからtrunkへのgradientだけを
   stop-gradientした対照を実装・実行。
3. no-auxをstep 300--400以上へ延長し、有限性を再確認。
4. admission-floor-only、write-budget-onlyを個別実行。
5. 最終候補は複数seed/resumeで失敗率として比較。

中期設計候補（まだ未実装・未検証）:

- hard実測write率を入力とする勾配外のfeedback controllerで、admission biasまたは
  thresholdを調整する。
- 勾配学習は「どのtokenを書くか」の順位付けを担い、write率はcontrollerで
  目標へ戻す。
- gate logitを線形領域へ留める弱い中心化正則化をablation候補にする。

PI制御は有望だが、積分wind-up、layer/bank別統計、分散環境での集約、
checkpoint/resume時のcontroller state、microbatch間の更新時点を先に仕様化する
必要がある。現時点では設計候補であり、採用確定とはしない。


18. 追加中の非有限診断
========================

現在のローカル変更ではtrain stepへ次を追加している。

- gradient_all_finite
- gradient_global_norm
- gradient_max_abs
- parameter_all_finite（optimizer更新直後）

CLIのrequire-finiteはlossだけでなく、`*_all_finite < 0.5`でも停止する。
これにより次回のstep 176近傍の再開実験で、少なくとも次を区別する。

- forward/lossが先に非有限化
- raw gradientが先に非有限化
- raw gradientはfiniteだがoptimizer update後のparameterが非有限化

25. Fableによる§15評価と現在の証拠による更新
=============================================

Fableの主要な指摘:

- no-auxではmemory residualが極小のままwrite policyが100%側へ漂流したため、CEは
  write rateを実質監督しておらず、auxがroutingの主目的関数になっている。
- 旧all-rejectとno-aux all-writeは、sigmoid両端の鏡像的な吸収状態である。
- no-aux step 220は既知のNaN窓244/248より前なので、安定性の証拠として不十分。
- self-index-only、次にtrunk stop-gradient版を優先すべき。
- write率をhard実測値に対する勾配外PI制御へ移す案には、Goodhart gap、飽和、
  急峻なaux gradientを同時に除く可能性がある。

その後に得た実測による更新:

- no-auxはstep 400まで延長し、この1 trajectoryでは全gradient/parameterがfinite。
- ただしwrite率は最終的に約4--5%へ移動しても、novelty=1、slot utilization=0.25、
  residual/base RMS比median 4.94e-6で、memory品質はcollapseしたまま。
- self-index-onlyはstep 300までfiniteだったが、step 117にgradient L2
  5.56e11という極端なspikeを記録し、その直後にほぼ全拒否へcollapseした。
  self-indexは重大な不安定化要因だが、NaNの必要十分条件ではない。
- budget-onlyはbudget lossが0のままstep 251でraw gradient NaNになった。
  corrected fixed-batch診断ではCE単独でも同じNaNを再現した。
- 従って現在の証拠は「aux値の急峻さだけがNaNを直接作る」より、auxがrouting/stateを
  危険な軌道へ動かし、その後CEのwrite-state backwardが非有限化する、を支持する。

PI制御案に対する現時点の立場:

- hard write率を直接制御してsoft/hard Goodhart gapを閉じる発想は採用候補として強い。
- ただしwrite率だけを5%へ保っても、no-aux runのようにmemory residualがほぼ0なら
  内容学習やcausal useは保証されない。
- PI controllerは「率の安定化」、ranking/content objectiveは「何を書くか」、
  causal-use/retrieval objectiveは「読む価値を作る」を別の契約として設計すべき。
- 実装前に、現在のportable v5 backwardの数値不安定性を修正する。コントローラを
  追加しただけでは、同じwrite-state gradient経路を通って再発する可能性がある。
